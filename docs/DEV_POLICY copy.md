# DEV_POLICY.md

AIエージェントとの対話による設計・実装協働プロトコル。

---

## 1. 目的とスコープ

- 目的: 人間とAIが対話しながら設計書を更新し、設計が固まった時点で git commit を行い、その後実装に入る。
- 対象: 本リポジトリの `docs/` 以下のドキュメントとソースコード
- 適用主体: AIエージェント（人間の手動操作には強制力を持たない）

---

## 2. フェーズ定義

### PHASE_0: ファストトラック（軽微修正・質疑・単一ファイル対応）

- トリガー: タイポ修正、軽微なUI/CSS調整、既知のバグ修正、仕様の質問
- AIの役割:
  - 設計書の更新や長大な確認対話をスキップし、即座に修正または回答を行う。
  - 設計書（`index.md` や各仕様書）への反映は原則不要（後でまとめてでも可）。

### PHASE_1a: 意図整理フェーズ（対話のみ）

- トリガー: 人間が「〜したい」「〜どうする？」「〜考えて」「〜について」と発話
- AIの役割:
  - 人間の意図を深掘り・質問・選択肢提示する
  - **設計書は更新しない。対話の流れを止めない。**
  - **コードは書かない。**
  - 方向性が固まったら、要約を提示して人間に確認する
- AIの振る舞い:
  - 人間の発話に対して「それでは以下の方向性で整理しました」という要約を提示する
  - 要約の例: 「ユーザー登録はメール認証なし、OAuthはPhase 2、パスワードは8文字以上。これで進めますか？」
  - 人間が「もう少し」「違う」「あと〜も考慮して」と言った場合、引き続き対話を続ける
- 終了の空気（以下のいずれか）:
  - 人間が「それでいこう」「OK」「その方向で」「書いて」と承認した場合 → PHASE_1b へ
  - 人間が「実装して」「コード書いて」と言った場合 → 文書化をスキップして PHASE_3 へ（例外セクションに従い decision-log.md に記録）

### PHASE_1b: 設計文書化フェーズ

- トリガー: PHASE_1a で人間が方向性を承認した後
- AIの役割:
  - PHASE_1a で整理・承認された内容を `docs/` 内の適切な設計書に一括反映する
  - `index.md` のステータスを `草案` に更新する（既に `確定` の場合は変更しない）
  - 変更後、「`api-design.md` と `functional-requirements.md` を以下のように更新しました」と報告する
- 禁止事項:
  - 承認されていない内容を設計書に書かない
  - 対話中の試行錯誤の痕跡（没案）を設計書に残さない
- 終了の空気:
  - 文書化が完了したら、人間の次の指示を待つ
  - 人間が「実装して」と言った場合 → PHASE_3 へ
  - 人間が「次は〜について」と言った場合 → PHASE_1a へ戻る

### PHASE_2: コミットフェーズ

- トリガー: 人間が「コミットして」と言った、またはPHASE_1b終了後に実装フェーズへの移行直前
- AIの役割:
  - `docs/` 以下の変更を git add / commit する
  - コミットメッセージ: `ai(docs): <変更内容>`
  - 人間がブランチ名を指定しない場合、変更内容に応じたブランチ名を提案する
- 原則: AIは自律的に push しない（人間が「pushして」と言った場合のみ）

### PHASE_3: 実装フェーズ

- トリガー: 人間が「実装して」「コード書いて」と発話
- AIの必須手順:
  1. `index.md` を確認し、実装対象に関連する設計書を特定
  2. 該当する設計書（`api-design.md` 等）を読み込む
  3. `CODING_RULES.md` を読み込む
  4. 実装を開始
- AIの振る舞い:
  - 「`api-design.md` の POST /users を実装します」など、根拠を明示する
  - 設計書と矛盾がある場合は、実装前に人間に確認する

## 3. 文書読み込み順序（選択的・ピンポイント読込）

原則としてファイル全体の丸読みを禁止し、必要なセクションのみを抽出して読み込む。

### PHASE_0（ファストトラック）
1. 設計書は読み込まず、対象コードのみを参照。

### PHASE_1a 開始時
1. `_ai_guide.md` — エントリーポイント
2. `DEV_POLICY.md` — 「2. フェーズ定義（PHASE_1）」セクションのみ参照
3. `index.md` — 議論に必要なカテゴリのみ部分参照

### PHASE_1b 開始時
1. 対象設計書（`functional-requirements.md` 等の該当セクション）

### PHASE_3 開始時
1. 対象設計書（`api-design.md` 等の今回実装する対象セクションのみ）
2. `CODING_RULES.md` — 該当言語の規約セクション
3. 既存の関連コード

## 4. 対話中の意識

### 設計対話中（PHASE_1a）
- 人間の発言が「設計の変更・追加」に相当する場合、即座に関連する設計書を更新しない。要約を提示する。
- どの方向性を整理したかを必ず報告する
- 人間が「一旦これで」と言うまで、実装の話を先取りしない

### 実装中（PHASE_3）
- 実装途中で設計書にない要件が必要になった場合:
  - 実装を一時停止
  - 人間に「これは `functional-requirements.md` に追加が必要ですが、どうしますか？」と確認
  - 人間の判断後、設計書を更新してから実装を再開

---

## 5. 対話中のメモ管理

PHASE_1a 中、AIは以下を遵守する：

- 対話の要約・整理結果は**AI自身のコンテキスト内**に保持し、ファイルには書き込まない
- 人間が「今の話をまとめて」と言った場合、要約を提示するが設計書には反映しない
- 新しいスレッドが開始された場合、以前の対話の要約は失われる可能性があるため、人間に「前回の方向性は〜でしたが、継続しますか？」と確認する
- PHASE_1a から PHASE_1b への移行時のみ、承認された要約を設計書に一括反映する

---

## 6. Git 操作

### commit
- 設計書の変更がまとまったタイミングで行う
- メッセージ例: `ai(docs): add user registration flow to usecases.md and api-design.md`

### push
- AIは自律的に push しない
- 人間が「pushして」と言った場合のみ実行

---

## 7. 例外

### 設計をスキップして実装してと言われた場合
- 警告を出す: 「設計書の更新なしで実装します。`decision-log.md` に記録します」
- 実装を実行するが、設計との乖離がある可能性を人間に伝える

### 実装中に設計の変更が必要になった場合
- 即座に設計書を更新し、人間に「実装に伴い `api-design.md` を修正しました」と報告
- その後実装を続ける
