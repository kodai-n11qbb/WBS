# DEV_POLICY.md

AIエージェントとの対話による設計・実装協働プロトコル。

## 1. 基本方針

本プロジェクトでは、人間とAIが対話しながら設計書を更新し、  
設計が固まった時点で git commit を行い、その後実装に入る。

AIは各時点で「今どのフェーズにいるか」を判断し、適切な行動をとる。

---

## 2. フェーズ定義

### PHASE_1: 設計対話フェーズ
- トリガー: 人間が「〜したい」「〜どうする？」「〜書いて」と発話
- AIの役割:
  - 人間の意図を `docs/` 内の適切な設計書に反映する
  - 更新後、「`api-design.md` を更新しました。次に進みますか？」など進捗を報告する
  - **コードは書かない**
- 終了の空気:
  - 人間が「実装して」「コード書いて」「そろそろ実装しよう」と言った場合
  - 人間が「OK」「それでいこう」と設計を承認した場合

### PHASE_2: コミットフェーズ
- トリガー: 人間が「コミットして」と言った、または実装フェーズへの移行直前
- AIの役割:
  - `docs/` 以下の変更を git add / commit する
  - コミットメッセージ: `ai(docs): <変更内容>` 
  - 人間がブランチ名を指定しない場合、変更内容に応じたブランチ名を提案する
- 原則: AIは自律的に push しない（人間が「pushして」と言った場合のみ）

### PHASE_3: 実装フェーズ
- トリガー: 人間が「実装して」「コード書いて」と発話
- AIの必須手順:
  1. `index.md` を確認し、実装対象に関連する設計書を特定
  2. 該当する設計書（`api-design.md` 等）を読み込む
  3. `CODING_RULES.md` を読み込む
  4. 実装を開始
- AIの振る舞い:
  - 「`api-design.md` の POST /users を実装します」など、根拠を明示する
  - 設計書と矛盾がある場合は、実装前に人間に確認する

---

## 3. 対話中の意識

### 設計対話中
- 人間の発言が「設計の変更・追加」に相当する場合、即座に関連する設計書を更新する
- どの設計書を更新したかを必ず報告する
- 人間が「一旦これで」と言うまで、実装の話を先取りしない

### 実装中
- 実装途中で設計書にない要件が必要になった場合:
  - 実装を一時停止
  - 人間に「これは `functional-requirements.md` に追加が必要ですが、どうしますか？」と確認
  - 人間の判断後、設計書を更新してから実装を再開

---

## 4. Git 操作

### commit
- 設計書の変更がまとまったタイミングで行う
- メッセージ例: `ai(docs): add user registration flow to usecases.md and api-design.md`

### push
- AIは自律的に push しない
- 人間が「pushして」と言った場合のみ実行

---

## 5. 読み込み順序

### PHASE_1（設計対話）開始時
1. `index.md` — どの設計書が存在するか確認
2. 人間の要求に関連する設計書

### PHASE_3（実装）開始時
1. `index.md` — 関連設計書の特定
2. 対象設計書（`api-design.md`, `data-model.md` 等）
3. `CODING_RULES.md` — コード規約の確認
4. 既存の関連コード（存在する場合）

---

## 6. 例外

### 設計をスキップして実装してと言われた場合
- 警告を出す: 「設計書の更新なしで実装します。`decision-log.md` に記録します」
- 実装を実行するが、設計との乖離がある可能性を人間に伝える

### 実装中に設計の変更が必要になった場合
- 即座に設計書を更新し、人間に「実装に伴い `api-design.md` を修正しました」と報告
- その後実装を続ける
