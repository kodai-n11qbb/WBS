変更耐性と拡張性を持つことを厳守して
- Dependency Injection: 具象クラスを直接 new せず、外から渡せ。（依存の整理）
- Rule of Three: 同じコードが3回出てくるまで、共通化・抽象化するな。（YAGNIの徹底）
- Refactor-ready Test: テストがないコードは、負債とみなす。（品質の担保）
- Performance Escape Hatch: 性能上重要な箇所（Hot Path）に限り、コメントで理由を明記した上で上記ルールを逸脱することを許可する。
- 実装途中で疑問があれば質問して。

## 便利ツールの試用・導入（Spike）
- **自発的探索**: UI検証や反復作業において、効率化できるCLIツール（playwright等）や軽量パッケージがあれば、AIから自発的に試用・提案してよい。
- **過去ログ確認（再検証防止）**: 新規ツール検討時はまず `docs/decision-log.md` を確認し、すでに採用または見送り済みのものは再検証しない（他スレッドの結果を再利用する）。
- **サンドボックス検証**: 新規ツールの導入時は、本番コードを直接書き換えず `scripts/` やテストコードで最小限の動作検証を行う。
- **撤退リミッター（トークン浪費防止）**: ツールの試用・設定で2回連続失敗した場合は深追いせず、即座に標準実装へ切り替える。
- **良否の報告と記録**: 「メリット（行数・速度）」と「リスク（依存度・サイズ）」を人間に提示し、採否（採用/見送り）に関わらず `docs/decision-log.md` に理由を1行記録する。
