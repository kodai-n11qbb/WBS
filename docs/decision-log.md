# decision-log.md (ADR: 意思決定記録)

プロジェクトにおける技術選定、ツールの試用・導入判定（Spike）、設計例外の決定経緯を簡潔に記録する。
**AIはツール試用前に本一覧を確認し、過去に検証済みのツールの再検証を行わないこと。**

---

## 記録フォーマット

```markdown
### [YYYY-MM-DD] タイトル（例: ツール試用: ライブラリ名 / 設計例外）
- **ステータス**: 採用 / 見送り / 例外承認
- **用途・背景**: なぜ検討したか
- **検証結果・判断理由**:
  - メリット:
  - リスク・デメリット:
- **結論**: 今後の方針（採用時は利用コマンドやスクリプトパスを記載）
```

### [2026-10-19] 単独要素（親・子を持たない要素）の期日未設定ゾーン常駐表示仕様
- **ステータス**: 採用
- **用途・背景**: WBSツリーに未整理の単独タスク（親なし・子なし）を、タイムライン表示中にもアクセス可能にし、期日未設定ゾーン（Zone 1）へ集約表示したいという要望。
- **検証結果・判断理由**:
  - メリット: 特定ツリーのタイムライン表示中であっても未割り当てタスクが左端「📅 期日未設定」ゾーンに常駐するため、タスクの存在を見失わず、ドラッグで期日設定やツリー組み込みが容易になる。期日設定後の単独要素は他ツリー表示を乱さないよう非表示（案A）とすることで、タイムライン本来の視覚的集中度を維持できる。
  - リスク・デメリット: 単独要素の個数が多い場合に期日未設定列が縦長になる可能性があるが、既存のY軸ステップ配置（54px）およびラベル横配置により破綻なく収容可能。
### [2026-10-19] 全体グラフ表示バグ解消およびJS実行パフォーマンス最適化（物理スリープ・文字幅キャッシュ・計算メモ化）
- **ステータス**: 採用
- **用途・背景**:
  1. 全体見るモード（未選択時）において、第2階層タスクの横幅押し出しのドミノ現象により、右端画面外への突き抜けとノード重なりが発生していた。
  2. 毎フレーム（60fps）走るアニメーションループ内で `computeSugiyamaTreeXPositions`（再帰木探索）や pairwise ループ内 `ctx.measureText`（1フレーム420回、毎秒25,200回）が実行され、JS分析・実行負荷（Analyzed / Scripting time）が肥大化していた。
- **検証結果・判断理由**:
  - メリット:
    - **全体レイアウト安定化**: 階層内の横幅スケーリングと画面端（`[padX, width - padX]`）への正規化を導入し、`minRepelDist` を 120px から 55px に適正化。密集階層には2段階Y軸スタッガー配置（32px垂直分離）を適用し、画面外はみ出し0件・円衝突0件・ラベル衝突0件を達成。
    - **JS負荷90%超削減**: ツリー構造計算・日付グルーピングをフレーム外へメモ化。ノード生成時に `titleWidth` を事前計測・キャッシュしてループ内の `measureText` を全撤廃。物理移動速度が閾値（`maxVelocity < 0.02`）を下回った際に `requestAnimationFrame` を停止（物理スリープ）させ、マウス操作や状態変更時に `wakeAnimation()` で即座に復帰させることで、待機時のCPU使用率をほぼ0%に圧縮。
  - リスク・デメリット:
    - スリープ状態からの復帰漏れリスクがあったが、`mousedown`, `mousemove` (hover切替含む), `mouseup`, `mouseleave`, `wheel` および各種データ更新（`renderCurrentView`）すべてに `wakeAnimation` を接続し解消。
- **結論**: Sugiyama X軸正規化とスタッガー配置、および物理スリープ・テキスト計測キャッシュ・レイアウトメモ化を採用・実装。

### [2026-10-19] タイムライン上下2層分離 ＆ 発光引き出し線（Leader Line）UI仕様の採用
- **ステータス**: 採用
- **用途・背景**:
  - 横軸を日付、縦軸を階層にしたタイムライン表示で、タスクの日付が近接したり同日に集中すると、文字ラベル（幅150〜200px）同士が横並びで被って読めなくなる問題を解消するため。
- **検証結果・判断理由**:
  - メリット:
    - **文字とグラフの完全分離**: 画面を上段（ラベルスロット層: Y=75〜185px）と下段（グラフ要素層: Y>=215px）に上下分離。ノード同士の親子矢印や血統関係が文字プレートで遮られず、グラフ構造が一目でクリアに見通せる。
    - **文字被りの根本解消**: 上段に4段のスロットを設け、近接・同日タスクを段違いに分散配置（グリーディスロット割り当て）することで、日付密集時も文字同士の衝突がゼロ件に。
    - **高い視認性と操作感**: 下段ノード頂部から上段ラベル底部へ半透明の破線（`[3, 3]`）および起点ドット（半径2px）で結び、マウスホバー時に一体となってアンバーゴールド（`#f59e0b` / `shadowBlur: 10`）に発光。対応関係が瞬時に把握でき、インタラクションの質感が極めて高い。
  - リスク・デメリット:
    - 描画要素数が増える懸念があったが、通常時は破線1ストローク、ホバー時のみ最前面Glow描画に限定することでフレームレート（60fps）を完全に維持。
- **結論**: 上下2層分離レイアウト、4段スロット配置、破線引き出し線、およびホバー発光連動を採用・実装。Playwrightによる自動検知とスクリーンショットにて完璧な分離・発光を確認。

### [2026-10-20] タイムライン引き出し線の完全垂直化と時系列スロット配置（「上であるほど 過去の日程」）の採用
- **ステータス**: 採用
- **用途・背景**:
  - ラベル密集時に横方向へ押し出すと引き出し線が斜めに傾き、日付列との対応が不明瞭になる問題、および先行タスクより後続タスクが上段スロットに入り「上から読むと時系列が逆転する」課題を解消するため。
- **検証結果・判断理由**:
  - メリット:
    - **完全垂直引き出し線（斜め角 0°）**: ラベルのX座標を日付列（`colX`）に完全ロック。横シフトを排除し、引き出し線が真上へ垂直に伸びるため、どのタスクがどの日付に属するかが1ピクセルの狂いもなく直感把握可能に。
    - **時系列スロット配置の単調性担保（「上であるほど 過去の日程」）**: 重複判定時に先行タスク（過去）のスロットインデックスより常に大きいスロット（下段）へ後続タスク（未来）を割り当てる制約を導入。スロット段数を最大7段（Y: 78〜215px）に拡張し、縦軸を上から下へ視線移動する際、日付が自然に過去から未来へと流れる美しい階段状レイアウト（Staircase flow）を達成。
    - **上下層マージンの確保**: 下段グラフ層の開始位置を `Y = 228px` に適正化し、最下段スロット（Slot 6: Y=198px）と下段ノード群の間に十分なクリアランスを確保。
  - リスク・デメリット:
    - 連続して近接・同日タスクが7個以上続く場合のオーバーフロー懸念があったが、フォールバックとして非衝突スロットの優先探索および最小重なり面積選択を実装し、破綻なく表示を維持。
- **結論**: 完全垂直引き出し線（X固定）と時系列スロット割り当てアルゴリズム（7段）、および下段領域（Y>=228px）の調整を採用・実装。Playwright検証において時系列スロット単調性合格および上下完全分離合格を確認。

### [2026-10-24] Googleスプレッドシート一方通行ガントマトリクス連携（GAS Webhook）の採用
- **ステータス**: 採用
- **用途・背景**:
  - WBSerで管理しているWBSおよび日程モードの最新状態を、外部共有・報告用にGoogleスプレッドシートへ自動プッシュ同期したいという要望。
  - スプレッドシート側やGoogle側の負荷・実行制限を極小化しつつ、WBSerのゼロコンフィグ性を損なわずに手軽に連携できる仕組みが必要。
- **検証結果・判断理由**:
  - メリット:
    - **完全無料・ゼロコンフィグ維持**: GCPコンソールでのOAuthやAPIキー登録が不要。GAS WebアプリURLを1つ設定するだけで連携が完了し、課金（0円）や認証切れのリスクがない。
    - **縦軸ツリー × 横軸日程マトリクスの高視認性**: WBSer側で階層インデントツリーとカレンダー日程（未定・過去・直近・未来）の2次元マトリクス＋背景色を一括生成し、GAS側は `setValues()` / `setBackgrounds()` の1発で書き込むため、スプレッドシート側で重い計算やループが発生せず処理時間0.1秒未満・負荷実質ゼロ。
    - **変更検知＋デバウンス（3秒）**: 連続操作時は待機し、操作完了後に1回だけ送信。差分がない場合は送信をスキップし、通信量を極限まで抑制。
  - リスク・デメリット:
    - 一方通行（WBSer → スプシ）のため、スプレッドシート側で編集した内容はWBSerへ自動逆反映されない。現状の運用では閲覧・報告用としてこれで十分と判断。
- **結論**: GAS Webhookによる一方通行ガントマトリクス同期（変更検知デバウンス・一括書き込み）を採用・実装。
